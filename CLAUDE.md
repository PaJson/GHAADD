# GHAADD - Project Memory & Architecture

> This file is versioned with the code (project memory for Claude Code and an architecture overview for contributors). Keep personal paths and secrets out of it.

## System Profile
- **Project Name:** GHAADD (GitHub Asset/Asset Downloader Daemon)
- **Tech Stack:** Python 3.10+ (Typing annotations required; `vermin` reports a code minimum of 3.9, 3.10 declared because 3.9 is EOL; developed and tested on 3.14), SQLite (WAL mode enabled), JSON Configs, Cross-platform Filelocks.
- **Dependencies:** `requests`, `python-dotenv`, `imapclient`, `filelock` (pinned lower bounds in `requirements.txt`).
- **Version:** see `modules/app_info.py` (the single source, used by `main.py` and the GUI window title; do not copy the number here)
- **Architecture:** Monolithic entry points (`main.py`, `main_gui.py`) orchestrating isolated, highly specific functional files within the `/modules` directory.

- `modules/cli_commands.py`: Argument parsing and dispatch for all CLI flags (queue, purge, report, doctor, lifecycle-log, etc.).
- `modules/config_manager.py`: Loads and validates `config.json` (including `terminal_log` settings). Writes go through `update_config(mutator)` / `set_config_values({"a.b": v})` (file lock + fresh re-read + atomic write; never write config.json directly). The daemon reads config once at startup, so saved changes apply on its next start.
- `modules/mapping_manager.py`: Owns `mapping.json` read/write/validation (`repository`, `folder`, `subfolder`, `destination`, `skiplist`, `recheck_intervals`, `limit`, `limit_folders`, `shared_destination` (true = this repository shares its destination folder on purpose; silences the shared-folder notice of `--mapping-validate`/Doctor once every repository of the group is marked), `sanity_check` (any_tag default / same_tag / off: which earlier release the SANITY_CHECK file-count warning in `queue_worker` compares with; `get_repository_sanity_check_mode`), `last_notification`, `last_finalized`, `active` (true = download; false = switched off, shown as "Inactive")). Key names changed in 2.0 (name/foldername/recheck_intervals_minutes/limit_release_type_folders/last_notification_seen/paused->active inverted): a file with the old names is understood in memory (`_upgrade_legacy_entry`), rewritten with a `mapping.json.v1.bak` backup by `migrate_mapping_file()` (GUI start, `ensure_mapping_file`, first write), and the upgrade waits while a daemon without `mapping_format` (older than 2.0, see `app_info.MAPPING_FORMAT` in the status file) runs. `mapping.example.json` shows the format. New entries get their `subfolder` and `limit` from `config.json` (`paths.default_subfolder`, default empty = no subfolder ("@GitHub" is the maintainer's personal choice, kept in his config.json); `processing.default_limit`, default 10; `config_manager.get_default_subfolder` / `get_default_repository_limit`, read at the moment the entry is created, Settings dialog fields). The GUI must go through this module.
- `modules/db_manager.py`: Structural manager for `state.db`. Controls the `job_queue` and the `lifecycle_events` logging tables.
- `modules/lifecycle_logger.py`: Writes queryable, structured event and cycle summary metrics directly to `state.db`.
- `modules/mailbox_listener.py`: Ingests incoming notifications, handles initial parsing, and hands tasks off immediately to the job queue.
- `modules/queue_worker.py`: Core processing daemon engine executing jobs via `PENDING`, `COMPLETED`, `FAILED`, or `SUPERSEDED` lifecycles. When a job's folder is finalized (`_finalize_staged_release_folder(connection=, job_id=)`, all four finalize paths) `_record_folder_size` measures it (`asset_downloader.measure_folder`) and ADDS it to `job_queue.folder_bytes` / `folder_files` (`db_manager.add_job_folder_size`, additive because a job can have a quarantined Partial folder as well as its finished one: both are measured after their move; NULL = jobs from before 2.4 or never moved; a failure is a `FOLDER_SIZE` warning, a dry run records nothing). `--purge-jobs` copies the measured sizes of the rows it deletes into the `job_size_archive` table first (`db_manager._archive_job_sizes`), and `get_job_folder_sizes` returns rows and archive together, so Stats data volumes survive a purge. Measuring is the daemon's job, never the GUI's.
- `modules/queue_reports.py`: Queue status/report/CSV output used by the CLI (and a candidate data source for the GUI). A job's `downloaded`/`skipped` counters describe its LAST check (later checks find everything unchanged, so a finished job reads `downloaded=0`); the job lines say "last check:" and add `brought_in=13 files / 398.2 MB` from the measured `folder_bytes`/`folder_files` (also `folder_bytes`/`folder_files` in `--json`). The counters themselves stay per-check on purpose: the worker's completeness test and the cycle summary rely on that.
- `modules/payload_types.py`: Shared typed structures (e.g. ingest/queue cycle stats).
- `modules/asset_downloader.py`: Independent component routing downloads via `mapping.json` paths.
- `modules/daemon_lock.py`: Handles singleton execution guarantees via the `filelock` dependency. Exposes `is_daemon_running()` / `get_daemon_status()` (running, pid, started_at, paused, next_poll_at, last_forced_poll_handled) for status probes; the daemon publishes poll state with `update_daemon_status()`.
- `modules/daemon_control.py`: Control channel for a running polling daemon, stored in the single-row `daemon_control` table of `state.db` (via `db_manager`). Writers (GUI/CLI) use `set_paused()` / `request_poll_now()` / `set_log_override()` / `set_push_override()` / `request_stop()` (graceful stop: the job in progress finishes, then the polling loop exits); the polling loop waits via `ControlWatcher.wait()`.
- `modules/log_files.py`: Terminal log files: naming (`YYYYMMDD_HHMMSS[_n].log`), `RollingLogFile` (size rollover at a line boundary, used as the TeeStream's file) and retention pruning. Also the place for the GUI log-tail helper's file discovery (`list_log_files`).
- `modules/stats.py`: the read-only `--stats` figures and the GUI's Stats window: `collect()` reads mapping.json and state.db (`db_manager.get_job_history`, `get_cycle_times`, `get_release_sizes`, `get_folder_counts`) and `build()` turns plain data into the report dict (mapping counts; jobs/polls/files/data per period 24 h/7/30/365 days/lifetime; 30-day daily series; top 10 busiest repositories, top 10 biggest repositories and releases; reliability; history age). `format_report()` is the CLI text, `period_rows`/`busiest_rows`/`biggest_rows`/`release_rows`/`summary_lines` feed both the CLI and `main_gui.StatsDialog` (Tools -> Stats; tabs Overview/Busiest/Biggest/Per day; collected in a thread). The CLI keeps the top 10 (`build(top=...)`, `None` = all); the dialog collects with `top=None` and a "Show" drop-down (`TOP_CHOICES`: Top 10/25/50/All) on the Busiest and Biggest tabs re-cuts the loaded report with `stats.limited()` without a new query (Copy as text gives what is shown); `list_titles()` words the headings ("Top 10 ..." / "All 143 ...") from `report["totals"]`. A Period bar (`PRESETS` + From/To fields, `StatsDialog._build_period_bar`) narrows Busiest, Biggest and Per day to a `stats.DateRange` (`parse_date`, `date_range`, `preset_range`; last day inclusive; `build(date_range=...)` adds a "range" row to the periods; sizes come from the measured folder of each job (`db_manager.get_job_folder_sizes`, passed to `build(job_sizes=...)`, dated by the job, each build its own row in Biggest releases via `MEASURED_MARK` keys): a reused tag such as "latest"/"continuous" has hundreds of jobs but `asset_state` holds only its newest build, so that alone undercounts; a release with no measured job (everything before the folder sizes were recorded) falls back to `asset_state`, dated by its first job or by its newest file (`get_release_sizes` `newest`) when that is later; purged releases only count in All time): the dialog calls `stats.load()` once and `stats.report_from()` on every change. The dialog is built withdrawn and shown by `StatsDialog._reveal` only when the data is in (`main_gui.reveal_window`: first mapped off screen beyond the desktop's right edge, laid out there, then moved into place in one step; the first map of a window otherwise lands at the screen corner. Do NOT use `-alpha` for this: Windows 11 still draws the frame of a transparent window, seen as an empty outline in the corner), so it opens once, filled and fitted, with no visible resizing. The optional `tkcalendar` (`requirements-optional.txt`; `main_gui.calendar_module()` is None without it) only adds a calendar button beside each date field that opens `DatePicker`, a panel drawn INSIDE the dialog (a `place()`d frame, not a window: a separate pop-up window was first placed by Windows at the screen corner and flickered; the dialog closes it on an outside click, Escape or a second click on the arrow); the typed fields always work. The CLI has the same controls: `--stats --stats-top N|all --stats-from YYYY-MM-DD --stats-to YYYY-MM-DD` (`cli_commands._stats_top` / `_stats_date`, listed in `MODIFIER_COMMANDS`; `collect(top=, date_range=)`). Data sizes (2.4+): the daemon measures each job's folder when it moves it (Complete and Partial, `queue_worker._record_folder_size`) and stores `job_queue.folder_bytes`/`folder_files`; Stats sums those per job, dated by the job's `created_at`, and `--purge-jobs` first copies them into `job_size_archive` (repo, tag, created_at, bytes, files) so a purge does not lose them. Why not `asset_state` alone: it is keyed by release (repo|tag) and keeps only the newest build, so a reused tag ("latest", "continuous", "nightly": hundreds of jobs on one key) undercounts, and `job_queue.downloaded_count`/`skipped_count` are the LAST check's figures (a later re-check overwrites them with 0 downloaded). `asset_state` stays only as the fallback for releases with no measured job (everything before 2.4); jobs before 2.4 are deliberately not backfilled. Known limit: after a purge the archive keeps sizes but not job counts or status. `--json` works with `--stats`. Tests: `tests/test_stats.py`.

- `modules/perf_report.py`: the read-only `--perf-report` diagnostics (sizes, growth, timings of the routine queries and probes; nothing is written). `main.py` skips its startup banner when `--json` is given so JSON output stays pure.

No restore command on purpose (documented as unzip over the originals). Tests: `tests/test_backup_manager.py`.
- `modules/log_tail.py`: toolkit-independent tail of the newest terminal `.log` file for the GUI's Terminal log tab (`LogTailer.poll()` returns only new lines; last 1000 lines on open, partial-line holdback, follows size rollovers via the `--- Log continued from X ---` header, reloads on truncation/huge backlog; `line_level()` for warning/error colouring).
- `modules/file_cache.py`: `StatCache` re-computes a value only when watched files' (size, mtime) changed (+30 s safety refresh); no watcher library on purpose (cross-platform, light). Used for the config settings/fingerprint and the queue summary (state.db + its -wal).

- `modules/viewer_push.py` + the `viewer/` folder (`ghaadd_viewer.py`, `Dockerfile`, `docker-compose.yml`, `.dockerignore`: self-contained, copy the folder to another machine; it is also the Docker build context, so the repo's config.json/.env/state.db can never be in it) (read-only **web viewer**, decided 2026-10-10): the daemon connects OUT to a standalone viewer and pushes snapshots; it opens no port. `SnapshotBuilder` builds the data the GUI loads (status, Mappings rows without `destination`, the four status lists via `gui_data.StatusFeed` with a null read-mark store, so nothing is written to config.json) with `redact_paths()` on every message (a path runs to the next comma/semicolon/closing bracket/quote, because real folder names hold spaces and brackets; tested against all messages of a real state.db); `ViewerPusher` is a thread (`push_once()` is one testable look: snapshot when the data hash changed or the viewer asked via `need_snapshot`, else a heartbeat every 15 s, goodbye on a clean stop, backoff 5-60 s on failure, one console line per new reason, never touches polling). Settings `viewer.enabled/url/token/name` (`config_manager.get_viewer_settings`, in the config fingerprint; read once at daemon start); live switch like the terminal log: `daemon_control.set_push_override` / `push_override` column / `ControlWatcher(on_push_override=)` / `reset_push_override_on_startup`, CLI `--push-on` / `--push-off`, `--new-viewer-token` prints a token and writes nothing; the daemon publishes `viewer_push` {active,last_ok,error} in the status file (`daemon_lock.read_published_status()` = the status without the lock probe, for code inside the daemon). `main.run_polling_loop` creates the pusher (not in dry-run) and stops it through `_viewer_push_scope`. `ghaadd_viewer.py` is ONE stdlib-only file (no imports from `modules/`, so it can be copied to another machine or into the Docker image): `Store` keeps the latest snapshot per daemon name in memory and decides live / lost (no message for `--lost-after`, default 45 s) / stopped (goodbye), and shows data ONLY while live (never stale numbers; a heartbeat after a gap asks for a new snapshot instead of reviving old data); `clean_data()` rebuilds a snapshot from the known fields only with capped sizes; tokens (`TokenBook`: `name=token` ties a token to one daemon name, a plain token is `*=token`; items split at comma/semicolon/newline; sources `--token`, `GHAADD_VIEWER_TOKENS` and the ONE file `config/.env` beside the script (`default_env_file()`; deliberately no `--env-file`/env-var override, so Docker and plain Python read the same place and compose mounts `./config:/app/config:ro`), merged; the file is re-read when its (mtime, size, inode) changes, looked at every 2 s, so tokens can be added or revoked without a restart; a file that disappears keeps the tokens known so far; `check()` never stops at the first match and returns ok / wrong_name (403) / unknown (401); at least 16 characters, refuses to start without a valid one and says which entry is bad without printing it); the token is judged BEFORE the body (a bad body is only a known sender's business), the name a sender claims is used only for the binding and for the list of refused senders (`Store.note_rejection`, shown as the page's "Rejected connections" panel: name, address, reason, count, age; the countdown is computed on the daemon's own clock (clock skew between machines); the page (inline HTML/JS, port 8888) builds everything with `textContent` (a test forbids `innerHTML` etc.) and has no controls at all: the viewer is passive by design, with no commands in either direction. ## Strict Guidelines & Code Style
- **Database Rules:** Never interact with `state.db` outside of `db_manager.py`. Multiple concurrent readers are supported via SQLite WAL mode, but mutating tasks require proper connection blocks to avoid lockouts.
- **State Centricity:** The old mailbox flag lifecycle is deprecated. Emails are read and deleted immediately on ingest; all pending status states live in the `job_queue` database layer.
- **Logging Standards:** Plain-text tracking (`Complete.log`, etc.) is retired. Use `lifecycle_logger` to output structured SQL records. 
- **Configuration Hygiene:** `config.json` uses `terminal_log.enabled` strictly to manage stdout mirrors (the startup default; a running daemon can be switched live, see Process Isolation); `terminal_log.max_file_mb` (default 10, 0 = no rollover) and `terminal_log.keep_files` (default 30, 0 = keep all) bound the log files. Rollover creates a newer-named file (never trims in place), so a tailing reader just switches to the newest file. Repository schedule overrides must go to `mapping.json` under `recheck_intervals_minutes`.
- **Process Isolation:** The GUI does not own the daemon process (the daemon may run as a Windows/Linux service). Agreed GUI model:
  - GUI is a read-only monitor plus a `mapping.json` editor; it reads `state.db`/`mapping.json`/`config.json` directly and uses `daemon_lock.is_daemon_running()` / `get_daemon_status()` for the running indicator.
  - Idle mode: the launchers (`daemon_launcher.build_start_command`, the systemd unit, the task, the LaunchAgent) run `main.py --daemon`, which is `--poll` except that `polling.enabled: false` makes the loop idle (`run_polling_loop(idle=True)`, `ControlWatcher.wait(idle=True)`: no countdown, one cycle per Poll now, status key `polling_idle`, control bar text "Polling is off: use Poll now"). `--poll` and a plain `main.py` keep their old meaning for CLI users (`--poll` always polls; plain = single run when disabled). Entries installed before `--daemon` existed keep running `--poll` until reinstalled.
  - Start button: enabled only when no daemon is running; launches `main.py --daemon` fully detached (`modules/daemon_launcher.py`, no console, own process group) so it survives GUI close. Its stdout is dropped (the terminal log mirrors it), stderr goes to `ghaadd.daemon.stderr.log` (gitignored) so a crash leaves a trace, and `PYTHONIOENCODING=utf-8` is set. `main._configure_output_encoding()` also forces UTF-8/`errors="replace"` on stdout/stderr: a redirected stdout used cp1252 and the first emoji print killed the daemon (found live 2026-10-06). The GUI reports a GUI-started daemon that exits by itself within 120 s. The terminal log file only starts for real run modes (`main()` starts it after the one-shot CLI commands have been handled), and the daemon publishes `log_active` in the status file so the "Terminal log" checkbox shows whether the file really opened (right after a click it shows what was asked for for ~2.5 s; the GUI reports it if the switch did not take).
  - Stop button: enabled only while a daemon is active; it only writes the graceful `request_stop()` (after a confirm dialog), never kills the process, and the GUI must never stop the daemon on its own close.
  - Control bar layout: three titled groups centred at the top, titles centred: Daemon (Start, Stop, Pause, "↻ Restart" only while needed), Polling (Poll now, Poll one, Check folders), Tools (Terminal log, Doctor, Stats, Settings…); `ControlBar` in `main_gui.py`. The daemon's status (dot, text, countdown) is in the window footer at the right (`ControlBar(status_parent=MainWindow.footer)`); the footer's left side shows the status messages (`set_status`) and its centre the job in progress while a cycle runs ("Processing 3 of 36: repo (type) tag @ commit"; the daemon publishes `queue_progress` {index,total,repo,tag,release_type,commit,since} in the status file from `queue_worker.process_queue_once` via `daemon_lock.publish_queue_progress`/`clear_queue_progress`, cleared in a `finally`; `gui_daemon.parse_progress`/`progress_summary`/`progress_detail`; tests `tests/test_queue_progress.py`), otherwise the queue figures (`MainWindow.queue_label`, updated each daemon-view tick from `gui_data.load_queue_counts`: `db_manager.get_pending_jobs` loaded per state.db change into `_PendingJob(next_check, later_steps)` where `later_steps` = `created_at + interval[attempt:]` (a job processed at attempt N runs step N and schedules step N+1 at created_at + interval[N]; the worker only ever gives a job ONE step per poll), the due/behind/catch-up counts follow the clock: "behind" = due and its next step is already past too; `gui_data.queue_text`/`queue_tip`; tests `tests/test_queue_counts.py`).
  - Control bar logic is toolkit-independent: `modules/gui_daemon.py` (`read_snapshot()`, `build_view()` texts/enabled states, `do_*` actions). A "↻ Restart" button (left of Settings) appears while a running daemon's settings differ from config.json: the daemon publishes `config_fingerprint` (`config_manager.get_config_fingerprint()`, a hash of the effective settings, ignoring the `gui` section) and the GUI compares; the button does a graceful stop, then starts a new daemon once the old one has exited. The daemon publishes the job in progress as `current_job` in `ghaadd.daemon.status.json` (`daemon_lock.publishing_current_job`, only while it holds the lock); the table shows it as the Running status.
  - Pause: a global pause now exists (`daemon_control.set_paused()`, CLI `--pause`/`--resume`): the countdown freezes and nothing polls until resumed, except that Poll now still works: it runs ONE cycle to the end (`ControlWatcher.forced_while_paused`, `checkpoint` ignores the pause for that cycle; Stop still applies) and the daemon stays paused; cleared on daemon startup. It is no longer needed for `mapping.json` safety (writes are locked). A per-repo `active` flag (false = switched off) also exists in `mapping.json`.
  - Terminal log switch: `daemon_control.set_log_override(True|False|None)` (CLI `--log-on`/`--log-off`) turns the `.log` mirror on/off in a running polling daemon (None = follow `terminal_log.enabled`). Session-only (cleared at daemon startup). Each switch-on opens a NEW `.log` file (no earlier output), switch-off closes it; the daemon applies it within ~1 s via `ControlWatcher(on_log_override=...)` and `main.TerminalLog`. The GUI toggle just calls `set_log_override`; the log tail follows the newest file.
  - Check folders: `daemon_control.request_check_folders()` (CLI `--check-folders`, GUI "Check folders" button next to Poll now) stores a stamp like poll-now; `ControlWatcher.wait(on_check_folders=...)` runs `main.run_folder_checks` (destinations present, `check_folder_limits`) once per new stamp without touching the countdown, paused or not. The same checks also run at daemon start and every `destination_check_every_n_polls` polls (0 = no automatic checks).
  - Poll now: `daemon_control.request_poll_now()` (CLI `--poll-now`) stores an epoch stamp; the daemon polls when the stamp differs from the last one it handled, then restarts its countdown. Pause takes effect at safe boundaries inside a running cycle (`should_pause=watcher.checkpoint` between emails and between jobs; a running job always finishes; leftover work stays PENDING/unread and runs right after resume). The daemon only reads the control row (except clearing `paused` at startup) and reports state via the status file.
  - All writes to `mapping.json` (daemon, CLI, GUI) go through `mapping_manager.update_mapping(mutator)` (file lock + fresh re-read + atomic write). The GUI edits via `update_repository_fields(repo, changes)`, `add_repository(repo, fields)` and `remove_repository(repo)` (all validated; catch `MappingValidationError`) and never sets the daemon-owned `last_notification` / `last_finalized`. Never write `mapping.json` directly.
  - **Renamed GitHub repos:** there is no rename operation. Add a new entry and remove the old one. The `repository` field (`owner/repo`) is the entry's identity and is read-only in the GUI. `job_queue.repo` / `lifecycle_events.repo` hold the same string as plain text, so old rows stay valid history.
- **Line endings:** LF everywhere (`.gitattributes` `eol=lf`, `.editorconfig`), on Windows too. Do not introduce CRLF.
- **Verification (end of every change):** after each code change, run the full unit tests (`python -m unittest discover -s tests -t .`) and the type check (`python -m pyright`, 0 errors) and only then report the work as done; say plainly if either is red or was not run. Add or update tests for new behaviour (toolkit-independent logic in `modules/`, widgets only as a thin layer; fake GitHub/IMAP/pystray/Tk-free helpers instead of the network). A change that only touches docs/comments needs neither. GUI changes also get a quick real-Tk smoke check (open the window against a temporary config/.env/mapping, never the real files) because the unit tests do not draw widgets: look for event loops (a `<Configure>` handler that changes its own size), blocked threads and Tk callback exceptions. Do not edit with `sed`/heredoc one-liners containing `
`, quotes or non-ASCII: use the Edit/Write tools, and re-read the diff of large edits (a mis-anchored slice once duplicated half of `main_gui.py`). There are no pyright exclusions: do not add files to an `ignore` list or loosen `pyrightconfig.json`; fix the type, or use a one-line `# pyright: ignore[rule]` with a stated reason (or make an annotation honest, e.g. `Optional[...]` for an argument the code already tolerates as None).
- **Comment style (applied to the whole codebase 2026-10-08):** every module, class and function (nested helpers too) gets a `"""docstring"""`: one summary line (imperative, "Return ...", "Build ..."), then at most 3-4 lines of why/how/gotchas, 5 lines in total, lines of at most 120 characters, no Args/Returns sections (the type hints carry that; mention a parameter only when its meaning is not obvious). Everything inside a function body is a `# comment`, never a bare string. Rationale that does not fit the docstring goes into a `#` comment at the code it explains. Avoid backslashes in docstrings (write "drive letter", not a path). Exceptions: `@overload` stubs and Protocol methods with a `...` body, which stay without a docstring. Tests are not covered by this rule.
- **Housekeeping:** this file is the project's status record (there is no separate task list); keep the roadmap below and the component map current with each change.
- **Commit messages and release notes:** write them in Markdown where possible (a short imperative subject line, then a body with bullet lists and `code` names). A release is an annotated tag `vX.Y` ("GHAADD X.Y") on a commit that sets `modules/app_info.py` `__version__`; the user makes the GitHub release from the pushed tag, so hand over the release notes as raw Markdown inside a fenced code block (use a four-backtick fence; the terminal renders plain Markdown, so a copy would lose the `##`/`-` characters), plus the release title on its own line.
